# Creational Design Pattern
This pattern control object creation by defining ***how*, *where* and *how* many objects should be created**.

*Creational design patterns define how an object is created, where the creation logic resides, and how many instances of an object should be created.*
| Pattern | How Object is Created | Where Creation Logic Lives | How Many Objects |
|-------|----------------------|----------------------------|------------------|
| **Singleton** | Controlled instance creation | Inside the class itself | Only one instance |
| **Factory Method** | Via a factory method | Factory class or method | Multiple instances |
| **Abstract Factory** | Via a group of factories | Factory family | Multiple related instances |
| **Builder** | Step-by-step construction | Builder class | One complex object |
| **Prototype** | By cloning an existing object | Existing object | Multiple cloned instances |

# 1. Singleton
Singleton is a creational design pattern that ensures a **class has only one instance/object** and provides a **global access point** to that instance/object.

### When to use
- Singleton is best used for stateless(does not store changing data) or immutable shared services like loggers or configuration managers (services common for all). Using Singleton to store mutable business state introduces global state, concurrency issues, and makes the system hard to test and scale.
- Configuration manager
- Logger
- Cache
- Thread pool
- Application-wide settings

### How to implement ?
- Private constructor
- Static instance reference
- Public method to access the instance (global access point)
- Instance is created **once**

### Spring Boot Perspective
- Bean is singleton by default
- Service is stateless
- Business data passed as method arguments
- Classes annotated with **@Service, @Controller, @Repository, or @Component are singleton by default**. This means only one instance exists in the application context.

### Guidelines:
- Do NOT use mutable global variables in singleton services
- Pass data through method parameters instead
- Keep services stateless to ensure thread safety and scalability

### Implementation
*Lets create Database as singleton class*

```java
class Database{
  public Database(){}  // wrong
 //If a class has public constructor that class can never become singleton becuase constructor always creates new object and return old one.

  private Database(){} // right Now no one can create object using constructor.
}
``` 

Now, Question is how an object will be created ?
ans :  we can create a method `getInstance()`,which will create an object of Database.

```java
class Database{
  private Database(){} 
  public Database getInstance(){
    return new Database();
  }
}
```

But again, Above approach gives access to other classes to create multiple objects of Database and we do not want that. what should be done next ?
ans : we can create an instance variable which would help us to check for the instance created or not.
```java
class Database{
  private Database instance = null;
  private Database(){} 
  public Database getInstance(){
    if(instance == null){
      instance = new Database();
    }
  return instance;
  }
}
```

Would other classes be able to call `getInstance()` method without creating an object of Database ?
ans : No, here come `static` in picture, we can make `getInstance()` as static method and since A static method can only directly access static variables. we need to make `instance` variable also static.
```java
class Database{
  private static Database instance = null;
  private Database(){} 
  public static Database getInstance(){
    if(instance == null){
      instance = new Database();
    }
  return instance;
  }
}
```
Now, Database class has become singleton. But there class in still not **thread safe** . 

If two threads call getInstance() at the same time:
- Thread A checks instance == null → true
- Thread B checks instance == null → true
Both create a new Database(), ❌ Result: Two instances, Singleton broken.

```java
class Database {
    private static Database instance;
    private Database() {}
    public static synchronized Database getInstance() {
        if (instance == null) {
            instance = new Database();
        }
        return instance;
    }
}
```
But After the first call:
- Object is already created
- No shared state is modified
- Still every thread waits for lock

This causes: unnecessary locking after initializati, Slow response, Thread contention, Poor scalability
```
Time →
T1: [LOCK] create instance [UNLOCK]
T2:      [WAIT] [LOCK] return [UNLOCK]
T3:            [WAIT] [LOCK] return [UNLOCK]
T4:                  [WAIT] [LOCK] return [UNLOCK]
```

**Double-Checked Locking** would be a better solution.

```java
class Database {
    private static Database instance;
    private Database() {}
    public static Database getInstance() {
        if (instance == null) {          // fast path (no lock)
            synchronized (Database.class) {
                if (instance == null) {  // lock only once
                    instance = new Database();
                }
            }
        }
        return instance;
    }
}
```
First thread : instance == null
→ enters synchronized
→ creates instance

other threads : instance != null
→ directly return instance
→ NO LOCK 

This approach is broken without `volatile`.
Lets understand this, 
JVM allows instruction reordering for performance optimization.
When an object is created, these steps are involved:
- Memory is allocated
- Constructor initializes fields
- Reference is assigned to the variable
Without volatile, the JVM may legally reorder these steps so that:
The reference is assigned before the constructor finishes
This means another thread may observe a non-null reference to a partially constructed object.
***This reordering is done for performance optimization.***
```java
class Database {
    private static volatile Database instance;
    private Database() {}
    public static Database getInstance() {
        if (instance == null) {          // fast path (no lock)
            synchronized (Database.class) {
                if (instance == null) {  // lock only once
                    instance = new Database();
                }
            }
        }
        return instance;
    }
}
```
JVM is not allowed to reorder writes to a volatile variable. volatile is applied to the instance variable because the problem is about how the object reference is written and read, not about how the method is executed.

**BEST PRACTICE IS TO USE ENUM**

Using an enum to implement Singleton is the safest approach in Java because JVM guarantees a single instance, thread safety, safe publication, and protection from reflection and serialization attacks.

```java
// Enum Singleton: Database
public enum Database {

    // The single instance
    INSTANCE;

    // Example state
    private int poolSize;
    private String connectionString;

    // Constructor (called exactly once by JVM)
    Database() {
        this.poolSize = 10;
        this.connectionString = "jdbc:mysql://localhost:3306/mydb";
        System.out.println("Database instance created!");
    }

    // Example method to access pool size
    public int getPoolSize() {
        return poolSize;
    }

    // Example method to set pool size
    public void setPoolSize(int poolSize) {
        this.poolSize = poolSize;
    }

    // Example method to get connection string
    public String getConnectionString() {
        return connectionString;
    }

    // Example method to simulate query
    public void executeQuery(String query) {
        System.out.println("Executing query: " + query);
    }
}
```

## Serialization and Reflection Attacks on Singletons

## 1. Serialization Attack

### What is Serialization?
- Conversion of a Java object into a byte stream to save to a file, database, or send over network.
- Deserialization reconstructs the object from the byte stream.

### How it can break Singleton
- Normal singleton instance can be serialized and then deserialized.
- Deserialization **creates a new object**, breaking the singleton property.

Example scenario:
- `db1 = Database.getInstance()`
- Serialize `db1` to file
- Deserialize as `db2`
- `db1 == db2` → false ❌

### How Enum prevents this
- Enum constants have **built-in `readResolve()`**.
- JVM ensures deserialization returns the **same enum instance**.
- `Database.INSTANCE` remains **single object** even after serialization.

---

## 2. Reflection Attack

### What is Reflection?
- Reflection is a Java feature to inspect and manipulate classes at runtime, often used in frameworks for dependency injection or serialization.
- Allows inspecting classes and invoking private constructors/methods at runtime.

### How it can break Singleton
- Private constructor can be accessed reflectively.
- New instances can be created bypassing singleton control.

Example scenario:
- Using `Constructor<Database>` with `setAccessible(true)`
- Calling `newInstance()` creates another object
- Singleton guarantee is broken.

### How Enum prevents this
- Enum constructors are **implicitly private**.
- JVM **throws exception** if reflection is used to create a new enum instance.
- Reflection attack is **impossible**.

## Summary Table

| Attack Type | Breaks Normal Singleton | Enum Protection |
|------------|------------------------|----------------|
| Serialization | Deserialization creates new instance | JVM ensures single instance |
| Reflection | Can call private constructor | JVM forbids reflective enum creation |
